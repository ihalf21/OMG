# OMG: Keycloak и безопасный деплой

Документ для подготовки деплоя OMG на корпоративный сервер с авторизацией через Keycloak и reverse proxy.

## Краткий вывод

Подключение Keycloak закрывает слой аутентификации: кто пользователь, как он вошел, активен ли его корпоративный аккаунт. Но Keycloak сам по себе не закрывает границу доверия между внешним клиентом, reverse proxy и Node.js backend.

Перед production-деплоем важно:

- не давать пользователям прямой доступ к Node.js порту;
- очищать входящие identity-заголовки на reverse proxy;
- выставлять trusted identity-заголовок только после успешной Keycloak-аутентификации;
- отключить fallback на `u-admin` в production;
- заранее завести первого администратора OMG с реальным Keycloak identity.

Рекомендуемая схема:

```txt
Пользователь -> HTTPS reverse proxy + Keycloak -> trusted headers -> Node.js OMG на 127.0.0.1
```

## Что закрывает Keycloak

Keycloak закрывает:

- аутентификацию пользователей;
- SSO;
- MFA, если включено на корпоративной стороне;
- политики паролей;
- централизованное отключение пользователей;
- передачу стабильной пользовательской идентичности в OMG.

В OMG пользователь может сопоставляться по одному из полей:

- `id`;
- `login`;
- `externalId`.

Практически лучше использовать:

- `externalId` = Keycloak `sub`;
- `login` = корпоративный логин или `preferred_username`;
- `displayName` = отображаемое имя пользователя.

## Что Keycloak не закрывает

Keycloak не решает эти задачи автоматически:

- проектные права внутри OMG;
- защиту от подделки identity-заголовков при прямом доступе к backend;
- отключение fallback-админа `u-admin`;
- backup/restore SQLite;
- совместимость версии Node.js с `node:sqlite`;
- конфликты одновременного сохранения;
- frontend UX при истекшей сессии;
- валидацию пользовательских URL;
- лимиты размера запросов на reverse proxy.

## Обязательные настройки reverse proxy

Reverse proxy должен:

- принимать внешний трафик только по HTTPS;
- проксировать OMG backend на `http://127.0.0.1:3001`;
- не открывать Node.js порт наружу;
- очищать входящие identity-заголовки от клиента;
- выставлять identity-заголовок только после успешной Keycloak-аутентификации.

Заголовки, которые нужно очищать на входе:

- `x-omg-user-id`;
- `x-auth-request-user`;
- `x-auth-request-email`;
- `x-forwarded-user`.

После Keycloak proxy должен выставить один согласованный заголовок, например:

```txt
x-auth-request-user: <preferred_username>
```

или:

```txt
x-auth-request-user: <email>
```

или:

```txt
x-auth-request-user: <keycloak_sub>
```

Важно заранее выбрать один стандарт и так же заполнить пользователей в OMG.

## Backend hardening перед production

Нужно внести или проверить следующие изменения:

- В production не должно быть fallback на `DEFAULT_USER_ID`.
- `OMG_DEV_USER_ID` должен работать только в явном dev-режиме.
- Если identity-заголовок отсутствует, backend должен возвращать `401`.
- Если пользователь не найден или неактивен, backend должен возвращать `401`.
- Node.js должен слушать только локальный интерфейс или быть закрыт firewall-ом.
- В production окружении не должно быть `DANGEROUSLY_DISABLE_HOST_CHECK=true`.

Рекомендуемая логика:

```txt
development:
  можно использовать OMG_DEV_USER_ID

production:
  identity обязателен из trusted header
  fallback на u-admin запрещен
```

## Первый администратор

Главный риск после отключения fallback: админский lockout.

Перед включением strict production mode нужно:

1. Узнать, какое значение Keycloak/proxy будет передавать в backend.
2. Завести в SQLite пользователя с этим значением.
3. Дать пользователю `globalRole = admin`.
4. Проверить `/api/me` через reverse proxy.
5. Только после этого отключать dev fallback.

Минимальные поля пользователя:

```json
{
  "id": "u-ivanov",
  "login": "ivanov",
  "displayName": "Иванов И.И.",
  "globalRole": "admin",
  "externalId": "keycloak-sub-or-empty",
  "active": true
}
```

## Возможные проблемы после подключения Keycloak

### 1. Все пользователи получают 401

Причины:

- proxy не передает identity-заголовок;
- OMG ожидает `login`, а proxy передает email или `sub`;
- пользователь не заведен в SQLite;
- пользователь заведен, но `active = false`;
- production fallback отключен, а первый admin не подготовлен.

Проверить:

```bash
curl -i https://omg.example.ru/api/me
```

Ожидаемо:

```txt
HTTP/1.1 200 OK
```

и JSON с текущим пользователем.

### 2. Пользователь вошел, но не видит проекты

Причина: Keycloak подтверждает личность, но доступы к проектам хранятся в OMG в `project_members`.

Решение:

- зайти под global admin;
- открыть администрирование;
- выдать пользователю роль `admin` или `lead` на нужных проектах.

### 3. Можно подделать пользователя через заголовок

Это критическая ошибка конфигурации.

Причины:

- Node.js доступен напрямую извне;
- proxy не очищает входящие `x-auth-request-user` и похожие заголовки;
- backend доверяет заголовку от недоверенного клиента.

Решение:

- закрыть прямой доступ к `:3001`;
- слушать backend на `127.0.0.1`;
- очищать auth-заголовки на proxy до Keycloak;
- выставлять trusted header только после успешной аутентификации.

### 4. Локальная разработка перестала работать

Это нормальное следствие отключения production fallback.

Решение:

- использовать отдельный dev auth mode;
- разрешать `OMG_DEV_USER_ID` только локально;
- не включать dev mode на production-сервере.

### 5. Сессия Keycloak истекла во время работы

Возможные симптомы:

- `/api/projects` или `/api/me` возвращают `401`;
- автосохранение перестает работать;
- пользователь видит ошибку загрузки или пустое состояние.

Рекомендация:

- на proxy настроить корректный redirect на Keycloak login;
- на frontend позже добавить понятное состояние "сессия истекла, войдите снова".

### 6. Увеличилось число конфликтов сохранения

После SSO появится реальная многопользовательская работа. OMG уже использует `revision` и возвращает конфликт при устаревшей версии проекта, но текущий UX требует обновить страницу.

Риск:

- пользователь может потерять локальные несохраненные изменения при refresh.

Рекомендация:

- для пилота достаточно предупредить пользователей;
- для активной эксплуатации добавить merge/diff или экспорт локальной версии при конфликте.

### 7. Большие проекты не сохраняются

Backend принимает JSON до `5mb`, но reverse proxy может иметь меньший лимит.

Рекомендация:

- синхронизировать лимиты request body на proxy и Express;
- проверить сохранение большого проекта после деплоя.

### 8. Notes не синхронизируются

Страница Notes хранит данные только в `localStorage` браузера.

Последствия:

- заметки не зависят от Keycloak-пользователя;
- заметки не доступны с другого компьютера;
- заметки пропадут при очистке browser storage.

Это не security-блокер, но важно для ожиданий пользователей.

## Preflight checklist

Перед деплоем:

- [ ] Node.js версии с поддержкой `node:sqlite` установлен на сервере.
- [ ] Выполнена проверка `node -e "require('node:sqlite'); console.log('sqlite ok')"`.
- [ ] `OMG_SQLITE_PATH` указывает на каталог вне Git working tree.
- [ ] `OMG_BACKUP_DIR` указывает на каталог вне Git working tree.
- [ ] У пользователя сервиса есть права на SQLite-файл и backup-каталог.
- [ ] Первый OMG admin заведен с реальным Keycloak identity.
- [ ] Production fallback на `u-admin` отключен.
- [ ] `OMG_DEV_USER_ID` не задан в production.
- [ ] Node.js порт недоступен извне.
- [ ] Reverse proxy очищает входящие identity-заголовки.
- [ ] Reverse proxy выставляет один согласованный trusted identity-заголовок.
- [ ] HTTPS включен на внешнем контуре.
- [ ] Лимит request body на proxy не меньше лимита backend.
- [ ] Настроен регулярный backup SQLite.
- [ ] Проведен тест восстановления backup на отдельной копии.

## Smoke tests после деплоя

Проверить healthcheck:

```bash
curl -i https://omg.example.ru/api/health
```

Проверить текущего пользователя через Keycloak/proxy:

```bash
curl -i https://omg.example.ru/api/me
```

Проверить список проектов:

```bash
curl -i https://omg.example.ru/api/projects
```

Проверить роли:

- global admin видит страницу администрирования;
- project lead видит только доступные проекты и может сохранять изменения;
- пользователь без доступа входит, но не видит проекты;
- неактивный пользователь получает `401`.

Проверить защиту от прямого доступа:

- внешний доступ к `http://server:3001` должен быть закрыт;
- запрос с поддельным `x-auth-request-user` напрямую к backend не должен быть возможен извне.

Проверить сохранение:

- изменить тестовый проект;
- убедиться, что изменения сохраняются;
- открыть проект вторым пользователем и проверить поведение при конфликте.

## Рекомендуемый порядок включения

1. Подготовить SQLite и backup-каталог.
2. Завести первого admin с Keycloak identity.
3. Настроить reverse proxy и Keycloak.
4. Проверить `/api/me` через proxy.
5. Закрыть прямой доступ к Node.js порту.
6. Отключить production fallback на `u-admin`.
7. Прогнать smoke tests.
8. Сделать backup.
9. Открыть доступ пилотной группе.

## Решение по риску

Без Keycloak и без hardening заголовков риск деплоя высокий.

С Keycloak, закрытым Node.js портом, очищенными trusted headers и отключенным production fallback риск снижается до приемлемого для пилота.

Для полноценной корпоративной эксплуатации дополнительно стоит закрыть:

- graceful UX для истекшей сессии;
- более безопасную обработку конфликтов сохранения;
- URL-валидацию;
- регламент backup/restore;
- регулярный dependency audit.
